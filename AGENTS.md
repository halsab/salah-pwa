# AGENTS.md

## Область действия

Эти инструкции применяются ко всему репозиторию. Если в подкаталоге появится свой `AGENTS.md`, он уточняет правила для этой части проекта.

## Документация

- Единственный источник проектной документации — папка [Salah-pwa на Google Drive](https://drive.google.com/drive/folders/1Mj0e00ee7n7R3rGS-oTZresvmA7uZ7Vp?usp=drive_link).
- Перед изменением поведения, архитектуры, данных, интерфейса или процесса выпуска изучай относящиеся к задаче актуальные документы в подпапке «Документация».
- Создавай и обновляй проектную документацию только в этой облачной папке. Не создавай в репозитории `README.md`, каталог `docs/`, дизайн-спецификации, планы или другие локальные копии документации.
- Если изменение кода делает облачную документацию неактуальной, обновляй соответствующий документ в рамках той же задачи.
- Лицензии, обязательные уведомления, инструкции для агентов и пользовательский контент не считаются проектной документацией и остаются в репозитории там, где нужны приложению или процессу разработки.

## Стек и ограничения

- Используй React 19, TypeScript в строгом режиме и Vite.
- Для IndexedDB используй `idb`; не обращайся к базе напрямую из UI-компонентов.
- PWA реализуй через `vite-plugin-pwa` и Workbox.
- Локальное состояние храни в React state и пользовательских hooks.
- Не добавляй роутер, глобальный state manager, UI-kit или другие крупные зависимости без подтверждённой необходимости.
- Следуй DRY, KISS и YAGNI. Предпочитай небольшие, явные и легко удаляемые решения.

## Архитектура

- Отделяй UI от IndexedDB небольшим типизированным слоем хранения.
- Выноси бизнес-правила, преобразования и вычисления в чистые функции.
- Оформляй каждое изменение схемы IndexedDB явной, последовательной миграцией.
- Держи компоненты сфокусированными; общую логику извлекай только при реальном повторном использовании.
- Сначала изучай существующие паттерны проекта и сохраняй их, если они остаются корректными.
- Комментируй по-русски только неочевидные инварианты, причины решений и сложные алгоритмы.

## Разработка через тесты

- Для нового поведения сначала добавляй или изменяй тест, наблюдай ожидаемое падение, затем реализуй минимальное решение и выполняй рефакторинг.
- Используй Vitest для чистых функций и модулей, React Testing Library с `user-event` для пользовательских сценариев, `jsdom` для DOM и `fake-indexeddb` для слоя хранения.
- Проверяй публичное поведение, а не внутреннее устройство компонентов.
- Для исправления дефекта добавляй регрессионный тест.
- Основной объём гарантий дают быстрые Vitest unit/integration-тесты. Новые регрессионные тесты оформляй по возможности на этом уровне; Playwright добавляй только для того, что действительно требует браузера.
- Во время разработки запускай только тесты затронутой области (`npx vitest run <путь>`). Не запускай полный набор и E2E ради мелких правок CSS, текста или разметки.
- Не ослабляй типизацию и не удаляй полезные проверки ради прохождения тестов.

## Порядок работы над задачами

- Для нетривиальных изменений сначала read-only изучи существующий код и тесты, найди место, которое действительно отвечает за нужное поведение, и определи минимальный набор файлов и изменений.
- Для нового поведения или исправления дефекта сначала добавь или измени релевантный тест, если это оправдано тестовой политикой выше; затем внеси минимальную реализацию.
- Запускай только релевантные тесты и проверки. Для значимых изменений перед завершением проведи отдельный review diff свежим контекстом.
- Не расширяй scope без необходимости. Мелкие CSS, текстовые и очевидные локальные изменения выполняй легко, без формального плана и лишних проверок.

## Интерфейс

- При переработке UI используй утверждённую спецификацию UI/UX и дизайн-системы из облачной документации.
- Новый визуальный язык: тёмный монохром, ровные заливки, Old Timey Mono, краткие подписи и капсулы. Цвета, типографика, отступы и границы утверждённого UX зафиксированы в спецификации.
- Проектируй mobile-first адаптивный интерфейс с учётом `safe-area-inset-*`.
- Обеспечивай полноценное управление клавиатурой и сенсорный ввод.
- Интерактивные цели должны быть не меньше 44×44 px.
- Уважай `prefers-reduced-motion`; движение не должно быть обязательным для понимания состояния.
- Для значимых визуальных изменений после реализации проверь итоговый интерфейс в реальном браузере: критичный сценарий на Mobile Safari/WebKit portrait, standalone PWA, safe-area и верхнюю/нижнюю системные зоны, вертикальный скролл и отсутствие горизонтального, основные состояния изменённого компонента. При изменении темы проверь затронутые светлые/тёмные или сезонные варианты; при изменении анимаций — `prefers-reduced-motion`.
- Если визуальное изменение затрагивает поведение, которого нет в существующем browser-сценарии, используй текущую Playwright-инфраструктуру. Маленькие изменения текста, цвета или локального CSS не требуют тяжёлой browser matrix. После обнаружения дефекта выполни только необходимое число корректирующих проходов.

## PWA и офлайн-режим

- Поддерживай корректный manifest и устанавливаемость приложения.
- Service worker должен обновляться автоматически и не оставлять интерфейс в несовместимом состоянии.
- После первого успешного запуска основные пользовательские сценарии должны работать без сети.
- Явно разделяй precache ресурсов приложения и runtime-кеширование данных; не кешируй чувствительные или непредсказуемые ответы без причины.
- Изменения PWA проверяй production-сборкой и offline smoke-test, а не только dev-сервером.

## Проверка и доставка

- Перед завершением изменения запускай только релевантные тесты, typecheck и production build в объёме, соразмерном изменению. Полный набор тестов и браузерный gate нужны для значимых изменений, а не для мелких CSS/текстовых/UI-правок.
- Обычный release gate: модульные тесты, production build, критический Chromium smoke, 4–6 критичных Mobile Safari/WebKit portrait сценариев, 2–3 offline сценария, 1 проверка обновления service worker и минимальные CSP/privacy проверки. Не повторяй одинаковые сценарии во всей browser/device matrix.
- Firefox, Mobile Chrome, iPhone landscape и расширенный cross-browser прогон — ручная/on-demand проверка (`npm run test:e2e:extended`) для browser-specific изменений и значимых релизов, а не часть обязательного deploy.
- `security:audit` и `license:check` запускай при изменении зависимостей (`package.json`, `package-lock.json`) и периодически; `actions:check` — при изменении workflow-файлов.
- Не дублируй typecheck: production build уже выполняет `tsc -b`.
- Перед релизом обязательны: воспроизводимая установка зависимостей, все тесты, typecheck, production build и offline smoke-test.
- GitHub Actions должен устанавливать зависимости из lock-файла, выполнять проверки и публиковать содержимое `dist` в GitHub Pages.
- Не скрывай ошибки CI, TypeScript, сборки или линтера отключением правил без документированной причины.
- Независимый review значимого diff должен проверить соответствие задаче, регрессии, лишние изменения, бизнес-логику, TypeScript/архитектуру, недостающие тесты, PWA/offline и затронутые области безопасности/privacy. Review сам по себе не требует повторять полный набор проверок; реальные замечания исправляй и перепроверяй только затронутую область.

## Работа с репозиторием

- Сохраняй пользовательские и несвязанные изменения; не выполняй массовое форматирование без необходимости.
- Делай минимальные сфокусированные изменения и не создавай преждевременные абстракции.
- Создавай локальные коммиты только по прямому запросу пользователя; такой запрос является достаточным разрешением на коммит.
- Не отправляй изменения и не переписывай историю Git без отдельного прямого запроса пользователя.
- Не выполняй без прямого явного разрешения пользователя destructive Git-операции, способные удалить или переписать существующие изменения: `reset`, `clean`, массовые `checkout --`/`restore`, force push, rebase/filter-rewrite, удаление веток с изменениями и эквивалентные команды. Сначала получи прямое подтверждение пользователя; обычные read-only Git-команды разрешены.
